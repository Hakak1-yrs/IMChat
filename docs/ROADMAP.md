## 阶段 1：服务端（核心）

现状：客户端直接读写共享的 `messages.txt`，只能在一台电脑上运行。

计划：

- **独立的 `IMChatServer`**，可以跨平台运行：Linux 上用 epoll，Windows 上用 WSAPoll，两者封装在同一个 `Poller` 接口下。
- **Reactor 线程模型**：一个 I/O 线程负责收发和分帧，业务逻辑交给工作线程池，结果再投递回 I/O 线程发送。
- **自定义协议**：`[4 字节长度][2 字节消息类型][JSON 正文]`。解码器负责处理半包和粘包，并限制单帧最大长度，防止恶意的超大长度把内存耗尽。
- **会话管理**：登录后服务端下发 token；心跳超时断开连接；客户端断线后自动重连，并补齐期间漏掉的消息。
- **消息可靠性**：
  - 客户端为每条消息生成 ID，服务端据此去重，这样客户端重发时不会出现重复消息。
  - 每个会话的消息按递增序号排序。
  - 服务端收到后回 ACK；对方离线时存为离线消息，上线后补发；支持已读回执。
- 现有业务类（账号、好友、群策略、朋友圈……）迁到服务端复用，控制台客户端和图形客户端只负责通信和显示。

## 阶段 2：存储

- 用 SQLite 替换文本文件：设计表结构和索引，修改操作放在事务里完成。
- 提供数据访问接口（Repository），以后可以平滑切换到 MySQL。
- 写一个迁移工具，把现有的文本数据导入数据库。

## 阶段 3：工程质量

- 测试框架换成 GoogleTest；为协议编解码和服务端逻辑补充单元测试和集成测试。
- 配置 GitHub Actions：Windows 和 Linux 上分别编译、跑测试；Linux 上额外开 AddressSanitizer / ThreadSanitizer。
- 写一个压测工具，模拟上千个客户端同时登录、收发消息，记录吞吐量和 p50/p99 延迟。
- 加入 clang-format、clang-tidy 和结构化日志。

## 阶段 4：功能

- 文件和图片传输：分块传输、断点续传、秒传（按哈希判断文件已存在就不再上传）
- 引用回复、转发、收藏、会话置顶和免打扰
- 多端同时登录、消息同步
