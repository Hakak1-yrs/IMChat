# 压测与性能优化

压测工具是 `IMChatBench`（[src/bench/main.cpp](../src/bench/main.cpp)），客户端用的就是项目自己的网络库：若干个事件循环线程，每个线程负责一部分 `TcpClient` 连接。

- 每个客户端一条连接，登录后给自己的好友连发私信（`--group` 时发到一个 100 人的群里）。
- 每条消息记录从发出到收到 `SEND_MSG_ACK` 的时间（回执延迟）。
- 统计对方实际收到的 `MSG_PUSH` 条数，确认一条不少。
- **窗口**：每个客户端同时在途的消息数上限。窗口为 1 时，一个客户端要等上一条的回执才发下一条（闭环），这时回执延迟约等于"客户端数 ÷ 吞吐"。

## 怎么跑

```powershell
build\bin\Release\IMChatBench.exe prepare bench_data 200    # 用业务接口注册 200 个账号，两两互为好友，前 100 人建一个群
build\bin\Release\IMChatServer.exe --port 9600 --data bench_data --rate-limit 0   # 压测时关掉每条连接的速率限制
build\bin\Release\IMChatBench.exe run --data bench_data --port 9600 --clients 200 --messages 250
build\bin\Release\IMChatBench.exe run --data bench_data --port 9600 --clients 100 --messages 20 --group
build\bin\Release\IMChatServer.exe --port 9600 --data bench_data --rate-limit 0 --storage sqlite   # 换成 SQLite 存储
build\bin\Release\IMChatBench.exe store store_bench sqlite 10000                                   # 只测存储层
```

## 结果

环境：Intel Core Ultra 7 255HX（20 线程）、16 GB 内存、Windows 11；服务端和压测客户端在同一台机器上，走回环地址。Release 构建。下表是单线程服务端（`--io-threads 0`，一个 `WSAPoll` 事件循环）的数据，多线程的结果见第 3 节。

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 私信，100 客户端 × 30 条，窗口 1 | 104 条/秒，p50 991 ms，p99 1435 ms | **38,183 条/秒**，p50 2.3 ms，p99 4.6 ms |
| 私信，200 客户端 × 250 条（共 5 万条），窗口 1 | —（太慢，没跑完） | **40,403 条/秒**，p50 4.8 ms，p99 9.1 ms |
| 私信，200 客户端 × 250 条，窗口 8 | — | **63,906 条/秒**，p50 19 ms，p99 39 ms |
| 群消息（100 人群），100 客户端 × 20 条，窗口 1 | 1,178 条/秒（每秒推送 11.7 万条），p50 85 ms | **15,879 条/秒**（每秒推送 157 万条），p50 5.5 ms，p99 10.9 ms |
| 群消息，100 客户端 × 50 条，窗口 4 | — | **17,795 条/秒**，p50 19 ms，p99 36 ms |

所有场景下推送都一条不少（群消息每条推给另外 99 人：2,000 条群消息 → 198,000 条推送全部收到），没有被服务端拒绝的消息。

## 发现的问题和优化

### 1. 每发一条消息都要把消息文件完整解析两遍

第一次压测，100 个客户端只有 **104 条/秒**，回执延迟中位数接近 1 秒，而且消息越多越慢（20 个客户端时是 183 条/秒）。

原因在 `MessageCenter`：为了让多个窗口（多个进程）共享同一个 `messages.txt`，每次查询都重新读取并解析整个文件。服务端处理一条私信时：
- `Platform::sendPrivate` 先 `syncSocial()`，要读一遍全部事件记录；
- 保存后，为了拿到这条消息的序号，又调用 `conversation()` 读一遍；
- 每次追加写还要打开、关闭一次文件。

文件里有几千条记录时，一条消息就要好几毫秒，而且随消息数线性增长。

**优化**：消息文件本来就是只追加、不改写的日志，所以可以增量读取。
- 解析结果缓存在内存里（按序号有序的 `std::map`），并记下解析到了第几个字节；
- 每次查询前先看文件大小，只读取、解析新追加的部分。只处理以换行结尾的完整行，别的进程写到一半的尾巴留到下次；
- 账号注销、群解散（`C` 记录）到达时，把此前与之有关的消息从缓存中删除；撤回（`W` 记录）就地标记。语义与原来逐行重放完全相同；
- 文件句柄一直打开着（读 + `FILE_APPEND_DATA` 追加写），省去每次打开、关闭的开销；
- 服务端取刚保存的消息改为 `lastFrom`：从最新的一条往前找，通常第一条就是。

多窗口同时运行时的行为不变：另一个进程追加的内容，下次查询时就会被读到。原有的 356 项业务测试（包括"两个窗口同时修改"的场景）全部通过。

结果：**104 → 27,188 条/秒（约 260 倍）**，并且消息数从 3 千增长到 5 万，吞吐也不再下降。

### 2. 群消息：同一份数据序列化 99 次、发送 99 次系统调用

增量读取之后，私信到了约 3 万条/秒，群消息却只有 1,178 条/秒（每条推给 99 人）。

- **只编码一次**：原来给每个接收者推送时，都要把同一个 JSON 重新序列化一遍。改为编码一次，同一份字节发给所有人：1,178 → 1,425 条/秒（+21%）。
- **合并写（write coalescing）**：真正的瓶颈是系统调用。原来 `TcpConnection::send` 只要输出缓冲区为空就立即调用 `send()`。群聊时，一轮事件循环里服务端处理了很多条群消息，同一个连接会在这一轮里收到多条推送，每条都是一次系统调用。

  改为：`send` 只把数据放进输出缓冲区，并在本轮事件处理完之后（事件循环的待办任务里）统一写出。同一轮里发给同一连接的多条消息合并成一次 `send()`。只在缓冲区从空变为非空时安排一次写，正在等可写事件时不重复安排。这样做没有引入额外的延迟：数据仍在本轮循环内发出，只是从"立即"推迟到"本轮事件处理完"。

  结果：群消息 **1,425 → 15,879 条/秒（约 11 倍）**，私信也从约 3 万提高到 4 万条/秒。

### 3. 多线程：I/O 线程 + 单个业务线程

单线程时，收发数据、切帧、解析 JSON 和业务处理都在一个线程里。改造方法：
- `TcpServer::setThreadCount(n)` 另开 n 个 I/O 线程，每个线程一个事件循环（one loop per thread）；
- 主循环只负责 `accept`，新连接按轮转分给某个 I/O 线程，此后这条连接的读写都在那个线程里；
- I/O 线程收到数据后切帧、解析 JSON，把一批解析好的请求一次性交给业务线程；
- `Platform`、会话表等业务状态仍然只在一个业务线程里访问，不需要加锁。

**第一版的问题**：线程越多，群消息越慢。8 个 I/O 线程时，群消息从 1.7 万条/秒跌到 **1,356 条/秒**，p50 延迟 291 ms。

原因：业务线程每推送一条，就向连接所在的 I/O 线程投递一个任务。I/O 线程比业务线程快，任务队列几乎总是空的，所以每条推送都要唤醒一次 I/O 线程（一次系统调用）。被唤醒的 I/O 线程每次只拿到一条数据，第 2 节的合并写也就失效了：99 次推送又变回 99 次唤醒加 99 次 `send()`。

**改进**：
- **业务线程发件箱**：业务线程处理请求时，要发的数据先放进发件箱；本轮处理完之后按 I/O 线程分组，每个 I/O 线程只投递一次。I/O 线程一次拿到一整批，同一连接的多条消息照样合并成一次 `send()`。关闭连接（比如挤下线时"发完通知再断开"）也走发件箱，与发送保持先后顺序。
- **减少唤醒**：`EventLoop::queueInLoop` 只在任务队列从空变为不空时才唤醒事件循环。事件循环每次进入等待前都会在锁内检查队列，所以不会漏掉任务。

| I/O 线程数 | 私信 200×250，窗口 1 | 群消息 100×50，窗口 4 |
|---|---|---|
| 0（单线程） | 41,195 条/秒，p50 4.8 ms，p99 5.8 ms | 17,673 条/秒，p99 35 ms |
| 2 | **66,379 条/秒**，p50 2.9 ms，p99 4.2 ms | 15,838 条/秒，p99 35 ms |
| 4 | 62,489 条/秒，p50 3.1 ms，p99 4.4 ms | 16,038 条/秒，p99 32 ms |
| 8 | 61,283 条/秒，p50 3.2 ms，p99 4.1 ms | 15,114 条/秒（第一版：1,356），p99 35 ms |

- 私信：2 个 I/O 线程时吞吐提高 61%，延迟也更低；再增加线程没有收益，因为瓶颈转移到了业务线程。
- 群消息：瓶颈一直在业务线程（保存消息、计算 @、组装 JSON、每条推送一个发送任务），所以加 I/O 线程没有提升；跨线程交接还有少许开销。把压测客户端的线程从 4 个加到 8 个，结果也不变，说明不是客户端的瓶颈。

服务端默认使用 2 个 I/O 线程（`--io-threads 0` 可以退回单线程）。全部服务端、客户端集成测试在 3 个 I/O 线程下再跑一遍（CTest 中的 `IMChatUnitTests.MultiThreadedServer`）。乱序重复运行 30 次，没有出现失败。

### 4. 存储：文本日志 vs SQLite

消息存储抽象成 `MessageStore` 接口，有两种实现：
- **文本日志** `MessageCenter`：只追加，增量读取；
- **SQLite** `SqliteMessageStore`：服务端用 `--storage sqlite` 选用。

同一组一致性测试分别验证两种实现，服务端和客户端的全部集成测试也在 SQLite 下再跑一遍。

`IMChatBench store <目录> text|sqlite` 不经过网络，直接测存储层：

| 操作（每次） | 文本日志 | SQLite（每次写入单独提交） |
|---|---|---|
| 保存一条私信 | 5.9 µs | 62 µs |
| 取回刚保存的那条 | 2.8 µs | 4.3 µs |
| 读社交记录 | 1.5 µs | 2.2 µs |

SQLite 的写入慢在**每条消息一个事务**：`BEGIN` / `COMMIT` 和事务管理的固定开销远大于插入本身。为此做了两步优化。

**批量提交（group commit）**
- 第一次写入时打开事务，并在事件循环本轮的待办任务里安排一次提交，本轮的所有写入合并成一个事务。
- 回执不能早于提交发出，否则服务端崩溃时，客户端已经收到回执的消息会丢失。所以存储批量提交时，所有发送都走发件箱，发件箱先提交、再发出回执和推送。"收到回执 = 已保存"这一点不变。

**检查点（checkpoint）移出写入线程**
- WAL 模式下，修改先写进 WAL 文件，再由检查点写回主库。默认的自动检查点会在某次提交时同步执行，那次写入就要多等几十毫秒。
- 改为：后台线程用自己的连接，每 200 毫秒做一次被动检查点（不阻塞读写）。
- 但写入一直不停时，后台检查点永远追不上最新的几页，WAL 不会从头复用：60,000 次写入后 WAL 长到了 **507 MB**。
- 于是在 WAL 超过约 16 MB 时，由写入方在提交后自己补做一次被动检查点（通过 `sqlite3_wal_hook`）。大部分页后台已经写回，这次只剩几页；做完后下一次写入从 WAL 开头重新写。WAL 稳定在几十 MB 以内。
- 中间还发现过一个 bug：后台连接打开后没有先执行任何语句，SQLite 认为它不在 WAL 模式，检查点什么也没做（返回的页数是 -1），数据一直堆在 WAL 里。修复前测得的"约 2.9 万条/秒"因此不可信，下表是修复后重测的结果。

同一时段、同一台机器，2 个 I/O 线程：

| 步骤 | SQLite 私信 200×250 | p99 |
|---|---|---|
| 每条消息单独提交 | 6,900 条/秒 | 73 ms |
| 批量提交 | 15,500 条/秒 | 50 ms |
| 批量提交 + 后台检查点 + WAL 回绕 | **约 22,000 条/秒** | 约 60 ms |
| （对照）文本日志 | 49,000 条/秒 | 5.5 ms |

群消息（100 人群，100×50，窗口 4）两种存储基本相同：文本日志 12,156 条/秒，SQLite 12,744 条/秒。瓶颈在推送，不在存储。

结论与取舍：
- SQLite 的私信吞吐约为文本日志的一半，p99 延迟更高。p99 的尖峰来自写入方补做的那次检查点：它要把数据刷到磁盘（fsync），这段时间业务线程在等。
- 换来的是事务、索引查询、崩溃后数据库不损坏，以及以后切换到 MySQL 等数据库的接口基础。
- 文本日志没有刷盘，断电时可能丢掉最后几条，但不会损坏文件（只追加）。
- 默认仍用文本日志：单机模式的多个窗口要共享同一个文件，SQLite 文件只给服务端这一个进程使用。

### 5. 群消息：业务线程里的热点

第 3 节的结论是：群消息受限于单个业务线程，加 I/O 线程没有用。

**为什么不把业务分片到多个线程**：这个系统里几乎每个操作都跨用户。发私信要读写双方的好友关系；群消息要读群成员、每个成员的在线状态和昵称；好友申请、群管理会同时改多个人的数据。按用户分片后，这些操作都要跨分片加锁或者两阶段处理，复杂度和出错风险都很大。所以先做另一件事：把业务线程里每条消息的工作量降下来。

先猜测、再优化，没有效果：
- 推送数据改为所有接收者共用一份（`shared_ptr`）；
- 发件箱改为类型化的条目（不再为每个接收者分配一个 `std::function`）；
- 拼接账号时复用同一个字符串。

这些改动让群消息只快了 1%～4%。

于是在业务线程处理群消息的各个阶段加计时（临时代码，测完删除），每条群消息：

| 阶段 | 耗时 |
|---|---|
| 保存 | 4 µs |
| 取回刚保存的消息 | 4 µs |
| 回执 | 4 µs |
| **组装推送的 JSON** | **28 µs** |
| 分发给 99 个接收者 | 8 µs |

组装 JSON 时要算这条消息 @ 了谁（`Platform::mentionsOf`）：对 100 个成员逐个取昵称，再看消息里有没有"@昵称"。取昵称用的 `findAccount` 是**逐个比较全部账号**的线性查找，200 个账号 × 100 个成员，一条消息就是约 2 万次比较，而且消息里根本没有 @ 时也照做。

两处修改：
- `mentionsOf`：消息里没有 `@` 字符就直接返回（绝大多数消息如此）；
- `findAccount`：改为哈希索引（"服务 账号" → 账号）。它几乎在每个请求里都会调用好几次，私信也跟着受益。

结果：组装 JSON 从 28 µs 降到 2.5 µs。同一时段测得：

| 群消息 100×50，窗口 4 | 优化前 | 优化后 |
|---|---|---|
| 单线程（`--io-threads 0`） | 14,459 条/秒 | **26,633 条/秒**（+84%），p99 23 ms |
| 2 个 I/O 线程 | 11,341 条/秒 | **19,896 条/秒**（+75%），p99 36 ms |

单线程反而更快：群消息每条要推给 99 个连接，交给 I/O 线程要跨线程投递，这个开销此时比收发本身还大。私信正好相反，2 个 I/O 线程时 52,355 条/秒，单线程时 35,135 条/秒。

教训：凭感觉做的三处"优化"几乎没有收益，真正的热点是一个线性查找。先测量，再动手。

### 6. 连接数扩展：2,000 和 5,000 条连接

用 `IMChatBench prepare` 注册 2,000 / 5,000 个账号，每个账号一条连接，压测客户端 8 个线程，私信，窗口 1。

| 连接数 | I/O 线程 | 全部登录用时 | 吞吐 | p99 |
|---|---|---|---|---|
| 2,000 | 0 | 1.63 s | 30,219 条/秒 | 84 ms |
| 2,000 | 2 | 2.16 s | 49,027 条/秒 | 47 ms |
| 2,000 | 4 | 1.63 s | 55,694 条/秒 | 41 ms |
| 5,000 | 0 | 5.75 s | 30,292 条/秒 | 171 ms |
| 5,000 | 4 | 3.44 s | 53,968 条/秒 | 106 ms |

所有场景下推送一条不少（例如 5,000 条连接时 50,000 条消息全部送达）。

- 连接多了以后，多 I/O 线程的收益比 200 条连接时明显：`WSAPoll` 每一轮都要把这个线程负责的全部连接交给内核检查，分到 4 个线程后每个线程只检查四分之一。
- 登录阶段的用时随连接数**超线性**增长：连接数是 2.5 倍，用时是 3.5 倍。这时每一轮只有少数连接有事件，却要扫描全部连接，总开销接近连接数的平方。这正是 poll 的固有局限，Linux 上的 `EpollPoller` 只返回就绪的连接，开销与连接总数无关。epoll 的实测要等 Linux 环境（CI 已配置）。
- p99 延迟随连接数上升，是闭环压测的必然结果：5,000 个客户端同时在等，回执延迟约等于"客户端数 ÷ 吞吐"（5,000 ÷ 54,000 ≈ 93 ms）。

### 7. 增量同步：只读需要的那一段

客户端重连后发 `SYNC_REQ { afterSeq }`，只要它离线期间的消息。原来的实现先用 `messagesFor` 把这个人的**全部**历史读出来，再跳过序号不大于 `afterSeq` 的部分。历史越长越慢，而且这是在业务线程里做的：一个老用户重连，其他所有人都要等。

改为存储接口新增的 `messagesAfter(…, afterSeq, limit)`，服务端多要一条来判断还有没有（`hasMore`）：
- 文本日志：消息本来就按序号存在 `std::map` 里，从 `upper_bound(afterSeq)` 开始，取够就停；
- SQLite：第一版把 `service`、`seq > ?` 写进 `WHERE … OR …` 的每个分支，每个分支都能走索引范围。只差最后几条时很快，但**第一次同步**（`afterSeq = 0`，只要 200 条）仍然慢：SQLite 的 OR 优化是把各分支符合条件的行全部取出来，再整体排序，然后才 `LIMIT`。
  第二版拆成 `UNION ALL`：我发的私信、发给我的私信、每个群各一段，每段 `ORDER BY seq LIMIT n`（沿索引按序号读，够 n 条就停），外层归并后再取前 n 条。

`IMChatBench store <目录> sqlite|text 50000`：这个人共有 125,001 条消息（10 万条私信 + 2.5 万条群消息）。同一时段测得：

| | 全部读出再跳过 | `WHERE … OR …` | `UNION ALL` | 文本日志 |
|---|---|---|---|---|
| 只差最后 20 条 | 107 ms | **38 µs** | 60 µs | 4.0 µs |
| 第一次同步，取 200 条 | — | 6.7 ms | **0.26 ms** | 17 µs |

`UNION ALL` 在只差几条时略慢（语句更长，每次都要重新编译：群号组合因人而异，不进语句缓存），但都在 0.1 ms 以内；第一次同步快 26 倍。两版结果完全相同（同一套一致性测试 `MessagesAfterReturnsOnlyTheNextPage` 分别验证两种存储）。

同样的问题还出现在群操作里：邀请、改公告等操作之后，要把新产生的系统提示推给成员，原来的做法是操作前、操作后各读一遍整个群的历史，用来找出新增的消息。改为操作前记下存储已分配的最大序号（新增的 `lastSeq()`），操作后用 `messagesAfter` 只读这之后的。对一个有 2.5 万条消息的群：

| 存储 | 原来（读两遍整个群的历史） | 现在 |
|---|---|---|
| SQLite | 2 × 14.5 ms | 0.04 ms |
| 文本日志 | 2 × 11.9 ms | 0.002 ms |

同步变成亚毫秒级以后，"把同步交给其他线程"的收益就不大了，所以暂时没有做（见"局限与下一步"）。

（单机模式的未读数 `unreadPrivate` / `unreadGroups` 也是先读出全部再按已读位置过滤：10 万条私信时约 19 ms。服务端不调用它们（未读由客户端按已读位置自己算），所以没有改。）

### 8. 好友、群的修改：一轮只保存一次

好友关系、备注、群资料保存在几个文本文件里。服务端每处理一次这类修改，就把这几个文件整体重新生成、写临时文件、`fsync`、改名替换（`ChatServer::persist`），保证回复"成功"时数据已经在磁盘上。

`IMChatBench save <数据目录>`（加一次好友 + 保存）：

| 账号数 | 200 | 1,000 | 5,000 |
|---|---|---|---|
| 每次 | 6.6 ms | 7.1 ms | 10.7 ms |

大部分是 `fsync` 的固定开销，和数据量关系不大。但这是在业务线程里做的：业务线程每秒最多处理一百多次这类修改，而且这期间所有人的消息都要排队。

用 `IMChatBench run --remark` 验证（200 个客户端，每个反复修改 20 次好友备注，窗口 1）：

| | 吞吐 | p50 | p99 |
|---|---|---|---|
| 每次修改都保存 | 129 次/秒 | 1,496 ms | 1,963 ms |
| 一轮只保存一次 | **15,089 次/秒** | **12 ms** | **17 ms** |

做法和 SQLite 的批量提交一样：修改时只做标记，发件箱在本轮交出回执之前保存一次。"收到成功 = 已经写入磁盘"不变——压测结束后直接强制结束服务端进程，200 个客户端各自最后一次修改的备注全部在文件里。保存次数在 `server.stats` 的 `dataSaves` 里可以看到；测试 `SocialChangesAreSavedBeforeTheReplyAndBatchedPerRound` 一次发出 50 个修改，检查回复前文件已经更新、保存次数少于修改次数。

修改越密集，一轮里攒的修改越多，平均到每次修改的保存开销就越小。这正是批量提交的好处。

### 9. 社交记录越多，私信越慢

好友申请、处理结果、单向删除、拉黑、验证设置都以记录的形式追加到消息存储里，`Platform::syncSocial` 按顺序把它们应用到内存中的好友表和黑名单（单机模式下多个窗口靠它同步彼此的修改）。每发一条私信之前都要调用一次，看看对方是不是刚删了我或拉黑了我。

问题在于它每次都调用 `records("FVDBS")` 把**全部**记录读出来（复制成 `Record` 对象），再跳过已经应用过的。前面的压测里账号都是直接加的好友，没有记录，所以没测出来。

`IMChatBench social <目录> text|sqlite <记录数>`：先写入若干条别人之间的好友申请记录，再测发一条私信要多久：

| 社交记录数 | 0 | 1,000 | 10,000 | 50,000 |
|---|---|---|---|---|
| 文本日志，原来 | 6.3 µs | 231 µs | 2,258 µs | 16,187 µs |
| 文本日志，现在 | 6.0 µs | 5.6 µs | 5.6 µs | 5.7 µs |
| SQLite，原来 | 93 µs | 691 µs | 6,334 µs | 34,814 µs |
| SQLite，现在 | 87 µs | 84 µs | 53 µs | 89 µs |

（这个工具直接调用 `Platform`，SQLite 没有开批量提交，每条私信单独一个事务，所以比文本日志慢；服务端会批量提交。）

原来有 1 万条记录时，业务线程每秒最多只能处理约 440 条（文本日志）或 160 条（SQLite）私信，而且记录只增不减，服务端运行得越久越慢。

改为存储接口新增的 `recordsAfter(kinds, afterLine)`，只读上次应用之后的新记录：文本日志在按行号排好序的记录里二分查找起点，SQLite 用 `line > ?`（主键范围）。处理"同意好友申请"时要找到当初那条申请：通常就在同一批新记录里，同意的是较早的申请时才把全部申请读出来。

还有一个细节：应用位置要前进到**最后一条记录**（`lastRecordLine()`，不分类型），而不是最后一条好友类记录。否则好友记录之后的几万条朋友圈记录，每发一条私信都要重新扫一遍（第 10 节的压测里发现的）。

**端到端验证**：`IMChatBench prepare <目录> 200 20000` 在压测数据里加 2 万条好友申请记录，用同一个压测客户端分别压改动前（a1eaaf4）和改动后的服务端，同一时段：

| 2 万条社交记录，200 个客户端私信 | 改动前 | 改动后 |
|---|---|---|
| 文本日志 | 178 条/秒，p50 1,071 ms | 63,867 条/秒，p50 3.0 ms |
| SQLite | 73 条/秒，p50 2,712 ms | 41,136 条/秒，p50 3.3 ms |

在原来的压测数据（几乎没有社交记录）上，改动前后的吞吐没有差别（文本日志都是约 6.7 万条/秒，SQLite 3.7～4.4 万条/秒，群消息都是约 3.5 万条/秒）：这几项优化解决的是"数据越积越多、越来越慢"，不是让空数据时更快。

（中间有一次测得"改动后"也只有 181 条/秒，查下来是 Release 版服务端没有重新编译，跑的还是旧代码。之后每次对比前都先重新编译全部目标。）

### 10. 朋友圈：内存索引

朋友圈的每个操作原来都要读出全部动态、点赞、评论记录再筛选：看朋友圈是这样，点赞、评论也是这样（为了确认能看到这条动态，先把查看者的整个朋友圈算一遍），朋友圈提醒也是。

改为 `MomentFeed`：一个由记录增量构建的内存索引（动态按序号、按作者，评论按序号，每个人收到的互动按先后），和社交记录一样每次只应用新记录。
- 看朋友圈：只遍历查看者自己和好友的动态（能看到的只可能是这些人的）；
- 点赞、评论、删除：按序号直接找到；
- 提醒：直接取"和我有关的互动"；
- 账号注销会让与它有关的旧记录作废（从存储里删掉），增量索引发现不了"少了几条"。所以存储记一个清除计数 `recordClears()`，计数变了就整体重建。单机模式下别的窗口注销账号，这边也能发现。

`IMChatBench moments <目录> text|sqlite <动态数>`：每条动态带一个赞、一条评论，大部分是陌生人发的，查看者能看到其中 1%：

| 1 万条动态（3 万条记录） | 看朋友圈 | 点赞 | 提醒 |
|---|---|---|---|
| 文本日志，原来 | 9.8 ms | 10.6 ms | 12.9 ms |
| 文本日志，现在 | 0.90 ms | 0.011 ms | 0.040 ms |
| SQLite，原来 | 21.9 ms | 21.6 ms | 22.8 ms |
| SQLite，现在 | 1.5 ms | 0.14 ms | 0.041 ms |

现在的耗时只和查看者能看到的内容有关（这里是 101 条动态），和全部动态的数量无关。SQLite 点赞的耗时主要是写入记录时的单独提交（这个工具没有开批量提交）。

好友申请也一样：列出"新的朋友"（`social.get`，客户端登录后、每次收到好友类的数据变化通知都会调用）原来要读出全部申请和处理结果。改为同样增量构建的 `FriendRequestBook`（按序号、按申请人和对方索引）。`IMChatBench social` 测得：

| 社交记录数 | 1,000 | 10,000 | 50,000 |
|---|---|---|---|
| 文本日志，原来 | 0.31 ms | 3.0 ms | 18.5 ms |
| 文本日志，现在 | 0.003 ms | 0.003 ms | 0.006 ms |
| SQLite，原来 | 0.68 ms | 7.0 ms | 36.6 ms |
| SQLite，现在 | 0.005 ms | 0.005 ms | 0.007 ms |

两个索引都在 `Platform` 加载数据时建好，第一次查询不用等。

### 11. 好友列表的查找：逐个比较 → 哈希索引

`FriendManager::contains` 原来逐个比较好友。判断是否互为好友、朋友圈的可见性、共同好友都要频繁调用它；联系人列表（`contacts.list`）要给每个好友算共同好友，开销是好友数的**三次方**。

`IMChatBench friends <目录> <人数>`：这些人两两互为好友，测一个人的联系人列表（每个好友的共同好友）：

| 好友数 | 100 | 300 | 600 |
|---|---|---|---|
| 原来 | 1.3 ms | 23.9 ms | 173.5 ms |
| 哈希索引 | 0.33 ms | 3.8 ms | 20.4 ms |

好友仍然按添加的先后保存在 `vector` 里（界面按这个顺序显示），另加一个"账号 → 位置"的哈希索引；删除好友时，后面的位置前移，索引跟着更新（删除很少发生）。剩下的耗时与输出成正比：600 人时共同好友一共有 35.8 万项。

群也是一样：按群号找群（每条群消息至少两次）逐个比较全部群，判断是不是群成员逐个比较成员。改为"(服务, 群号) → 群"的哈希表，每个群另存一份成员集合（成员只通过 `addMember` / `removeMember` 两个函数增减，列表和集合保持一致）。`IMChatBench groups <目录> <群数>`，每群 50 人：

| 5,000 个群 | 原来 | 现在 |
|---|---|---|
| 按群号找群 | 2.66 µs | 0.02 µs |
| 列出我所在的群（每人约 1,250 个） | 549 µs | 179 µs |

## 局限与下一步

- 业务处理仍在一个线程里（理由见第 5 节）。最重的只读查询（离线同步）已经改成只读需要的那一段（第 7 节），不到 1 毫秒；以后如果有更重的只读查询，可以交给其他线程：SQLite 的 WAL 模式下，另开的只读连接读到的是最近一次提交，不阻塞写入。
- SQLite 的 p99 尖峰：可以把最后那次检查点也挪到后台线程，在业务线程空闲时用 RESTART 检查点完成 WAL 回绕；或者接受 `synchronous=OFF` 的风险（断电时数据库可能损坏）。
- 不同时段的绝对数字会波动（同一份代码，笔记本的电源模式和温度不同时，相差可达 40%）。所以每张表都是在同一时段测得的，只比较同一张表里的数字。
- `WSAPoll` 每轮都要把全部连接交给内核检查，连接数上万时会成为瓶颈；Linux 上换成 epoll（`Poller` 接口已经留好）。
- 压测客户端和服务端在同一台机器上，会互相争用 CPU；跨机器的测试还没有做。
